# Shared serial recovery

`jukuhost --recover-session` owns discovery, disk service, rediscovery and
reconnection. Juku stock/JF17 and C11/C12 use native protocol handlers. POSIX
Kaypro V3, Robotron W4 and stock 1715 use the same control loop with supervised
protocol helpers; the CP/M repositories expose this as their launcher `auto`
mode. Explicit boot/attach and legacy W2/W3 commands remain available.

The host first listens for a complete checked NetDisk request at the saved
runtime settings. It preserves that request and its unread tail. After three
seconds without one it calls the profile helper. Juku remains receive-only;
Kaypro requires a nonce/CRC-checked V3 reply, W4 its checked identity/handshake,
and stock 1715 its 12 12 handshake. Unknown state never authorizes an upload.
The helper verifies artifacts, uploads only after identification, and returns
serial settings. The host waits for a checked runtime request before serving;
it does not race the guest with an unsolicited ready marker after execution.

During service, 15 seconds without a valid request triggers rediscovery for
helper profiles. Normal polls/requests keep the connection active. Reset ROM
identification causes the same platform to boot using the existing private
disk. No recovery path replaces the session disk. Existing journal validation
and read-only policy remain in force. Cache epochs are allocated persistently
under a global lock, advance past copied sessions, and never wrap. Confirmed
boots discard queued console input and clear the corresponding terminal.

Serial loss reopens the configured device path, never an arbitrary adapter.
Custom PL2303HXD configuration is shared by Kaypro and W4. It matches the serial
path through IORegistry, verifies revision and USB line coding, and records USB
location identity for subsequent recovery. PTYs never access USB. Runtime
settings are restored after a reopen; an unchanged prepared descriptor is not
reprogrammed during ordinary discovery. Unplugging or swapping an adapter is
not a way to select a different computer.

## Helper contract, version 1

The native runner takes `--recovery-python`, `--recovery-helper`, and
`--recovery-config` with `--recover-session`. These are generated by launchers,
not shell command strings. The helper runs synchronously with the borrowed
serial descriptor and a separate result descriptor. Only one process performs
serial I/O at a time. Cancellation/deadline expiry kills and reaps the helper.
Python is not required for native Juku recovery.

A JSON configuration binds the profile driver, source image, platform, helper
modules and host executable by SHA-256. It includes the session directory,
selected device, boot/runtime settings and profile options. `prepare` restores
settings only when necessary and allocates an epoch. `discover` performs the
profile's bounded ROM exchange and bootstrap. Each operation records a JSON
result; `recovery-state.json` is the last helper result, while native `phase=`
logs are authoritative for current service state. ROM identity is retained as
`last_rom`, not misrepresented as a new response during CP/M attachment.

The 16-byte result is `JHR1`, status byte (0 unknown, 1 booted, 3 serial disconnected), parity ASCII,
stop bits, reserved zero, little-endian uint32 baud and epoch. Invalid results,
helper failure and unsafe execution stop recovery. Serial loss returns to the
shared reopen/discovery path. W4 execution-acknowledgement loss returns to
discovery without replay; a Kaypro CRC NAK requires fresh ROM identification
before another upload. There is no automatic
LOAD/EXEC replay after an uncertain stock 1715 transfer. That loader has no
checksum/acknowledgement; operator reset is required before another attempt.

## Verification

`tests/jukuhost_profile_recovery_test.py` exercises exact first-frame/tail
preservation, noise, unknown state, uncertain execution and helper cancellation.
Existing native runner, protocol, journal and Juku recovery tests remain gates.
The CP/M repositories test actual ROM/platform execution, host replacement and
modeled power cycles with independent file verification. Emulator results do
not qualify a physical link or promote experimental baud-rate defaults.
